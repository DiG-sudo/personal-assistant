## 为什么选择 MaiBot

[MaiBot](https://github.com/Mai-with-u/MaiBot) 明确面向日常聊天、人类式交互和发言时机；仓库页面核查约 6.7k stars，README 将 main 标为稳定分支，并有发布和长期维护记录。选它主要因为目标与“活人感”直接吻合，社区规模和版本维护作为辅助依据；源码存在不代表已验证本项目的互动效果。

本轮沿用已核查的源码修订 `2a9af62cec37035d29237acbe2cf3adceb700b27`，重点读取 Planner、Replyer、消息调度及 wait / stop 的真实调用链。当前是设计阶段，没有安装或运行参考项目，也没有修改本项目运行代码。

## 核心逻辑：两层配合

| 实现层 | 具体负责什么 | MaiBot 源码依据 |
| --- | --- | --- |
| 提示词控制 | Planner 理解场景、当前话题及回应对象，决定发言、等待或结束；发言时提供回复方向。Replyer 结合人格和风格生成自然的可见表达 | R48 的 maisaka_chat.prompt；R49 的动作处理；R61 的 reply_reference 与 Replyer 调用；R62 的 maisaka_replyer.prompt |
| 事件与状态控制 | 接收消息、收齐一批输入、安排推理；执行等待/结束状态，到时或在符合条件的新消息到来时重新判断；让模型决定真正改变执行行为 | R59 的 MessageTurnScheduler；R26 补读的 runtime 状态与超时路径；R07—R08 的 wait / stop；R60 的空闲退避 |

Planner 与 Replyer 是语义决策和表达生成的分工，不是新增业务模块。是否分成独立模型调用、采用哪种输出协议，在具体实现时结合现有执行链确定；凡实际新增的模型请求都必须计入预算。

主链路：

```text
新消息 / 等待到期 / 明确来源的外部事件
  → 事件层判断何时进入推理
  → Prompt 指导理解话题并选择下一步
      → 发言：形成回复方向 → 按人格生成可见回复
      → 等待：记录等待条件 → 到期或允许的新消息触发后重看
      → 结束：本轮收住 → 后续有事件再进入
```

上图是借鉴 MaiBot 后对本项目的逻辑映射，不表示现有 Runtime 已支持全部分支。

## 活人感具体体现在哪

| 体验目标 | 核心策略 | 来源与本项目取舍 |
| --- | --- | --- |
| 听完一段再接 | 在需要时把连续输入视为同一段话，结合整批语境判断，减少只听半句就回复 | 参考 R59 和 R26 的消息防抖；按私聊实际需要决定，不预设固定睡眠时间 |
| 接话有对象、有话题 | 模型判断正在回应谁、当前最该接哪件事；把上下文和回复方向交给表达生成 | R48、R61、R62；用户资料和共同经历继续来自记忆，不编造 |
| 有时开口，有时收住 | 发言、等待、结束具有明确含义；等待后根据新情况重看，话题结束时允许停下来 | R07—R08、R49；当前私聊的明确任务仍须得到处理，不复制群聊发言概率 |
| 表达有稳定底色，又贴合当下 | Replyer 使用人格、回复风格、目标消息与当前回复方向；关注已经回应过的内容，减少重复 | R23 补读、R61—R62；继续使用本项目 lively-companion 人格，不复制 MaiBot 的具体身份 |
| 活跃时跟得上，空下来能停 | 事件驱动新的判断，无事时减少重复进入；明确提及和新情况按规则唤醒 | R59—R60 与 R26；参考项目的退避部分仅用于群聊，本项目按场景取舍 |

这里的“活人感”指可观察的互动质量：是否理解完整输入、接住话题、适时收尾以及表达自然。人为加随机延迟、随机忽略用户或设置亲密度数值不作为第一版必需机制。

## 与当前项目的接入边界

行为提示词与人格分别维护。人格决定长期性格与表达底色，行为决定这一次何时回应、回应对象及回应目的；已有的人格示例继续保留，避免同一规则在两处重复改写。

事件调度由 Harness 外的业务组件产生，通过 ConversationService 的会话串行入口进入；Harness 承担恢复、上下文准备、检查点与执行生命周期，Runtime 保持模型/工具循环和实际预算。模型选择的等待/结束由明确的执行结果和状态承接，不把调度器、社交状态或业务工具名直接写进 Runtime。

当前 Runtime 仍拒绝空最终回答，现有 HTTP 和检查点也未定义社交式等待/静默。后续接入前先明确这些动作的返回、持久化、唤醒和失败语义；不能将空文本当作已支持的停顿。当前阶段不接入上下文，不增加平行聊天记录，不默认后台轮询或额外情绪模型。

## 后续设计顺序

先以 MaiBot 为主线确定当前私聊中发言、等待和结束的含义，再编写行为 Prompt，最后落实必要事件和执行边界。一次只实现有当前需求的机制；源码证据和本项目改动分别标注。
