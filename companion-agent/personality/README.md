`Personality` 是独立的不可变内容对象，保存核心设定、表达约定和对话示例。 `text()` 按这个顺序生成提示文本，示例标记为风格参考。应用目前使用通用系统提示词，人格接入上下文待开发。

## 内置人设

完整文本在 [Personality.lively()](../../src/main/java/com/guodi/assistant/component/personality/Personality.java) 中。

| 方面 | 第一版设计 |
| --- | --- |
| 身份与相处 | AI 助手，像熟悉、好聊、有自己判断的搭档；不预设姓名、年龄、性别或恋爱关系 |
| 性格底色 | 活泼、跳脱、好奇，能接梗和适度拆台；有判断、愿意说明分歧，关心具体而不奉承 |
| 抽象方式 | 意外但能理解的比喻、冷面笑话、一本正经的荒诞联想；能跟着用户把话题接回来 |
| 黑色幽默 | 调侃荒诞处境、失控计划和日常小灾难，善意且适量；不以真实痛苦取乐 |
| 自然程度 | 口语化，通常一两个自然段；允许不玩梗，不重复口头禅，不强迫每轮追问 |
| 场景收放 | 认真求助、明显低落、重要决定和技术问题优先直接清楚地回应；用户要求时立即收住玩笑 |
| 长期一致性 | 不编造共同经历或记忆；真实偏好与经历仍由记忆提供，临时状态与时机仍归行为 |
| 示例覆盖 | 八组：闲聊、需求变更、拖延、疲惫、明确难受、技术解释、纠正误解和缺少历史记录 |

两段表达示例：

> 用户：需求又改了，昨天白干。  
> 助手：昨天的方案今天就办上赛博葬礼了。先别全推倒，看看哪些还能拆下来继续用。

> 用户：别开玩笑了，我这次真的挺难受。  
> 助手：好，我认真听。刚才发生了什么？你想先说说，我就先听着。

这份人设已能独立生成文本，尚未经过真实模型对话验证。文本约定的表达效果不等于已经具备记忆能力或主动行为。

## 已明确的边界

| 事项 | 当前决定 |
| --- | --- |
| 所属位置 | 人格属于 ContextBuilder 的上下文内容，不增加独立人格执行循环 |
| 配置与加载 | 启动装配提供固定内容，ContextBuilder 负责组织模型输入 |
| 逻辑归属 | 用户资料和共同经历归记忆；临时情绪、主动联系和回应时机归行为 |

## 人格内容结构

以下是提示词的内容段落，不是新的业务模块。

| 内容 | 包含什么 | 当前状态 |
| --- | --- | --- |
| 核心设定 | 身份、核心性格、价值取向、相处方式；可按需要包含明确标记的虚构背景 | 已写入第一版，不编造真人背景或共同经历 |
| 表达约定 | 语气、回复长短、幽默和关心方式；不同场景中的表达原则 | 已写入第一版，实际效果待接入后校准 |
| 对话示例 | 少量代表性输入和理想回复，用于呈现性格 | 第一版八组已编写 |

示例作为明确标记的风格参考，不作为已发生的聊天、共同经历或工具结果。第一版围绕已明确方向设计，没有补造姓名、年龄、性别或真实用户资料。

## 当前 WindowContextBuilder 链路与人格位置

人格接入仍是待实现设计。

### 当前调用链

| 时机 | 调用链 | 实际行为 |
| --- | --- | --- |
| 启动装配 | AssistantAutoConfiguration.contextBuilder → WindowContextBuilder | 从配置路径读取系统提示词，将文本与窗口预算传入 Builder |
| 每轮开始 | Runtime.chat → Harness.aroundRun → restoreHistory / recallMemory → Runtime.runLoop | 恢复聊天、保存 RUNNING，并召回本轮记忆快照 |
| 每次推理 | Runtime.runLoop → Harness.aroundReasoning → ContextBuilder.prepare → Prompt → aroundModelCall / Runtime.callModel | 先提交本次需应用的 steer，重建模型视图；Harness 附加工具定义，Runtime 检查最终预算并调用模型 |
| 工具之后 | 保存工具结果检查点 → 下一次 aroundReasoning / prepare | 使用本轮最新已提交消息重建上下文，保持工具请求与结果配对 |
| 本轮完成 | 提交 COMPLETED → MemoryModule.observe → 返回 Reply | 记忆维护发生在回答成功保存后；当前不会在每次 prepare 中重新 recall |

### 当前消息顺序

| 顺序 | 分组 | 消息形态 | 当前选择规则 |
| --- | --- | --- | --- |
| 1 | 系统提示词 | 一个 SystemMessage | 使用启动时已校验的完整 systemPrompt；当前尚无独立人格输入 |
| 2 | 记忆数据 | 可选的一个 UserMessage，含 memory 数据围栏 | 按传入顺序挑选至记忆字符预算；某条放不下则跳过继续；没有选中内容则省略 |
| 3 | 已完成历史 | 按原角色展开的 user / assistant / tool 消息 | 从最新向前选 COMPLETED 整轮，受轮数和历史字符预算约束；整轮放不下则停止；最终按旧到新顺序排列 |
| 4 | 本轮消息 | 完整展开 activeTurn 的已提交消息 | 保留用户输入、已应用 steer、assistant 工具意图、tool 结果及其他已提交消息；不参加历史窗口裁剪 |

默认配置中：历史最多 8 轮、24000 字符；记忆 4000 字符。本轮完整消息和系统提示词仍受 Runtime 最终总字符预算约束，默认总上限 64000 字符。

工具定义不由 WindowContextBuilder 加入上述消息组，而由 Harness.aroundReasoning 通过 ToolCallingChatOptions 交给 Prompt；工具执行结果则属于历史或本轮消息。

### 人格应该插入哪里

人格固定内容放在第一组系统上下文中，基础规则之后、记忆与历史之前。ContextBuilder 可以把基础规则和人格文本组合为一个 SystemMessage。

下图沿用当前四组顺序用于标注人格位置。针对缓存的后续目标是段内追加、阈值压缩，动态内容随本轮追加并保持可重建，详见 [上下文与缓存设计](../CONTEXT.md)；不是仅靠每轮重新排列四组即可完整复用历史。

```text
1. SystemMessage
   ├─ 基础规则
   └─ 人格
      ├─ 核心设定
      ├─ 表达约定基线
      └─ 对话示例

2. UserMessage：召回记忆数据
   └─ 后续可包含有来源的表达偏好或表达经验

3. 已完成历史：整轮、旧到新、保留工具配对
4. 本轮完整消息：输入、steer、assistant、tool 等
```

学习结果属于数据补充，不直接改写第一组已发布的人格文本。人格组合代码放在 component/context，固定内容由启动配置提供；Runtime/Harness 不解释人设内容。

## 逐步完善：固定核心与可积累表达

启动时确定的核心文本提供稳定的性格设定。人格提示词提供底色，记忆与行为可以让表达逐步贴合用户；这些仍属于既有三块，不新增“进化模块”。

| 完善方式 | 怎样变化 | 本项目归属 |
| --- | --- | --- |
| 用户偏好积累 | 例如用户明确说“可以抽象一点，但不要句句都玩梗”，保存这一表达偏好 | MemoryModule 保存带来源的偏好；ContextBuilder 召回并作为数据提供，不覆盖核心人格资源 |
| 表达习惯积累 | 从真实交流提炼“某种场景适合怎样表达”，后续按场景选择使用 | 候选和来源可放在记忆中；选择与使用属行为，ContextBuilder 只组织选中内容；当前未实现 |
| 核心人格迭代 | 将长期有效、经过整理的设定或示例写成下一版人格提示词 | 通过配置更新核心内容 |

### 本项目当前选择

用户已明确偏好“活泼、跳脱、抽象、带一些黑色幽默”；已按这一方向实现内置人设，后续根据真实对话反馈校准程度。

当前先完成独立人格类，后续再实现资源加载与上下文接入；初期通过明确反馈积累表达偏好。自动提炼表达作为后续可选能力，需明确来源、纠正方式、使用范围与调用预算。若引入额外模型学习，必须有显式执行与计数机制，不能在记忆 observe 或上下文构建中无预算地调用。

可参考的后续流程（设计建议，尚未实现）：

```text
真实交流与明确反馈
  → 带来源的偏好或表达候选
  → 筛选、纠正与场景选择
  → ContextBuilder 组织为本次参考数据

经过整理且适合长期固化的内容
  → 调整人格提示词
  → 下一次装配明确选择
```
