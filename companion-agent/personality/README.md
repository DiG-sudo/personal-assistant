## 第一版独立类（已实现，未接入上下文）

源码：[Personality.java](../../src/main/java/com/guodi/assistant/component/personality/Personality.java)。采用不可变 record，不注册 Spring Bean，不依赖 Runtime、Harness、ContextBuilder 或存储；构造对象不会让人格自动生效。

| 字段 / 方法 | 含义 |
| --- | --- |
| revision | 复用 ExecutionManifest.Ref，显式传入人格 id 和内容版本；拒绝空身份、空版本和 latest |
| coreSetting | 核心设定文本 |
| expression | 固定版本的表达约定基线 |
| dialogueExamples | 对话示例文本；输出时明确标记为风格参考、非真实聊天记录 |
| text() | 按核心设定、表达约定、对话示例的固定顺序生成完整文本 |
| sha256() | 复用 Fingerprints，计算 text() 的 UTF-8 SHA-256；从内容直接推导，不另存一份可写文本或校验和 |

普通构造器保持调用方提供的三段字符串，允许尚未填写的段落为空字符串；完整的第一版内置人设通过 Personality.livelyV1() 获取，其三段内容均已编写。测试另有用于验证数据类的测试人格，不作为其他预设发布。

区分两种版本：类的实现行为声明为 personality@1.0.0；revision 表示调用方提供的某套人格内容版本，二者独立。内容或示例变化要声明新内容版本，文本组织行为变化要新增实现版本并保留旧实现。当前类不维护版本目录，也不在不同对象之间强制绑定 id/version 与内容；已发布内容的不可覆盖及校验和核对由后续资源与装配边界落实。

当前提供显式的 livelyV1() 入口、构造、文本与内容指纹；不自动选择预设，不加载资源、不生成 PromptSnapshot、不写入 manifest，也不调用模型。下文“版本装配方案”仍是后续设计，不能作为已经生效的配置。

检查：[PersonalityTest.java](../../src/test/java/com/guodi/assistant/PersonalityTest.java)。已运行 `mvn -o -Dtest=PersonalityTest test`，编译及 3 个本地测试通过，包含内置人设的固定内容指纹；未调用外部模型。

## 第一版具体人设：lively-companion@1.0.0

入口：`Personality.livelyV1()`。本次先将内容直接固定在这个类的方法中，满足独立类阶段的范围；完整文本以源码为准，不在文档再维护一份。将来迁入版本化资源时仍需保持这份内容和旧入口的可定位性。

| 方面 | 第一版设计 |
| --- | --- |
| 身份与相处 | AI 助手，像熟悉、好聊、有自己判断的搭档；不预设姓名、年龄、性别或恋爱关系 |
| 性格底色 | 活泼、跳脱、好奇，能接梗和适度拆台；有判断、愿意说明分歧，关心具体而不奉承 |
| 抽象方式 | 意外但能理解的比喻、冷面笑话、一本正经的荒诞联想；能跟着用户把话题接回来 |
| 黑色幽默 | 调侃荒诞处境、失控计划和日常小灾难，善意且适量；不以真实痛苦取乐 |
| 自然程度 | 口语化，通常一两个自然段；允许不玩梗，不重复口头禅，不强迫每轮追问 |
| 场景收放 | 认真求助、明显低落、重要决定和技术问题优先直接清楚地回应；用户要求时立即收住玩笑 |
| 长期一致性 | 不编造共同经历或记忆；真实偏好与经历仍由记忆提供，临时状态与时机仍归行为 |
| 示例覆盖 | 八组：闲聊、需求变更、拖延、疲惫、明确难受、技术解释、纠正误解和缺少历史记录 |

两段表达示例：

> 用户：需求又改了，昨天白干。  
> 助手：昨天的方案今天就办上赛博葬礼了。先别全推倒，看看哪些还能拆下来继续用。

> 用户：别开玩笑了，我这次真的挺难受。  
> 助手：好，我认真听。刚才发生了什么？你想先说说，我就先听着。

这份人设已能独立生成文本和指纹，尚未经过真实模型对话验证。文本约定的表达效果不等于已经具备记忆能力或主动行为。

## 已明确的边界

| 事项 | 当前决定 |
| --- | --- |
| 所属位置 | 人格属于 ContextBuilder 的上下文内容，不增加独立人格执行循环 |
| 配置与加载 | AssistantAutoConfiguration / 发布装配负责读取并校验明确版本，将不可变快照传给 ContextBuilder；Builder 不在每轮推理时重新读文件 |
| 版本粒度 | 基础系统规则与人格提示词分别版本化，组合后形成模型输入 |
| 生效时机 | 应用启动/重新装配时选择；轮次创建时冻结实际配置；不实现运行期间文件热加载 |
| 人设内容 | 已实现 lively-companion@1.0.0；完整内容在 livelyV1()，后续按新版本迭代 |
| 逻辑归属 | 用户资料和共同经历归记忆；临时情绪、主动联系和回应时机归行为 |

用户本轮明确要求人格独立版本化，因此此前“基础规则和人格合成一个源文件版本”的建议已被取代。旧建议仅保留在历史开发日志中，不作为当前实现依据。

## 当前 WindowContextBuilder 链路与人格位置

以下“当前”描述已核查的运行代码；人格独立版本组合仍是待实现设计。

### 当前调用链

| 时机 | 调用链 | 实际行为 |
| --- | --- | --- |
| 启动装配 | ReleaseManifestFactory.loadPrompt → PromptSnapshot → AssistantAutoConfiguration.contextBuilder → WindowContextBuilder | 读取清单指定的通用系统提示词并校验 SHA-256，将文本与窗口预算传入 Builder |
| 每轮开始 | Runtime.chat → Harness.aroundRun → restoreHistory / recallMemory → Runtime.runLoop | 恢复聊天、固定本轮 manifest、保存 RUNNING，并召回本轮记忆快照 |
| 每次推理 | Runtime.runLoop → Harness.aroundReasoning → ContextBuilder.prepare → Prompt → aroundModelCall / Runtime.callModel | 先提交本次需应用的 steer，重建模型视图；Harness 附加工具定义，Runtime 检查最终预算并调用模型 |
| 工具之后 | 保存工具结果检查点 → 下一次 aroundReasoning / prepare | 使用本轮最新已提交消息重建上下文，保持工具请求与结果配对 |
| 本轮完成 | 提交 COMPLETED → MemoryModule.observe → 返回 Reply | 记忆维护发生在回答成功保存后；当前不会在每次 prepare 中重新 recall |

### 当前消息顺序

| 顺序 | 分组 | 消息形态 | 当前选择规则 |
| --- | --- | --- | --- |
| 1 | 系统提示词 | 一个 SystemMessage | 使用启动时已校验的完整 systemPrompt；当前尚无独立人格输入 |
| 2 | 记忆数据 | 可选的一个 UserMessage，含 memory 数据围栏 | 按传入顺序挑选至记忆字符预算；某条放不下则跳过继续；没有选中内容则省略 |
| 3 | 已完成历史 | 按原角色展开的 user / assistant / tool 消息 | 从最新向前选 COMPLETED 整轮，受轮数和历史字符预算约束；整轮放不下则停止；最终按旧到新顺序排列 |
| 4 | 本轮消息 | 完整展开 activeTurn 的已提交消息 | 保留用户输入、已应用 steer、assistant 工具意图、tool 结果及其他已提交消息；不参加历史窗口裁剪 |

默认 session-v1 清单中：历史最多 8 轮、24000 字符；记忆 4000 字符。本轮完整消息和系统提示词仍受 Runtime 最终总字符预算约束，默认总上限 64000 字符。

工具定义不由 WindowContextBuilder 加入上述消息组，而由 Harness.aroundReasoning 通过 ToolCallingChatOptions 交给 Prompt；工具执行结果则属于历史或本轮消息。

### 人格应该插入哪里

人格固定内容放在第一组系统上下文中，基础规则之后、记忆与历史之前。由新版本 ContextBuilder 组合两份独立校验的快照，模型侧可以仍保持一个 SystemMessage。

下图沿用当前四组顺序用于标注人格位置。针对缓存的后续目标是段内追加、阈值压缩，动态内容随本轮追加并保持可重建，详见 [上下文与缓存设计](../CONTEXT.md)；不是仅靠每轮重新排列四组即可完整复用历史。

```text
1. SystemMessage
   ├─ 基础规则（已有独立版本）
   └─ 人格（新增独立版本）
      ├─ 核心设定
      ├─ 表达约定基线
      └─ 对话示例

2. UserMessage：召回记忆数据
   └─ 后续可包含有来源的表达偏好或表达经验

3. 已完成历史：整轮、旧到新、保留工具配对
4. 本轮完整消息：输入、steer、assistant、tool 等
```

学习结果属于数据补充，不直接改写第一组已发布的人格文本。人格组合代码放在 component/context 的新行为版本中，版本读取与校验放在 config 装配；Runtime/Harness 不解释人设内容。

## 版本装配方案

设计方向是沿用已有加载、校验和快照能力，为 ContextBuilder 增加人格输入。以下路径和键名是示意，尚未在代码中注册。

| 对象 | 版本与来源 | 用途 |
| --- | --- | --- |
| 基础系统提示词 | 既有 prompt 的 id/version/resource/sha256 | 工具协议、真实性和数据边界等基础规则 |
| 人格提示词 | 独立 personality 的 id/version/resource/sha256，建议资源位于 prompts/personality/<id>/<version>.txt | 人格设定、表达约定与示例 |
| ContextBuilder | 选择包含人格组合行为的新组件版本，保留 window@1.0.0 | 将两份已校验内容组合为系统上下文，再选择记忆与历史 |
| 执行快照 | 基础提示词沿用 ExecutionManifest.prompt；人格快照拟经 ContextBuilder 的 ConfigurationSnapshot 记录 | 保存实际人格的 id/version/resource/sha256/完整 text，使配置可定位且参与指纹 |

人格快照可以复用现有 PromptSnapshot 值类型及校验思路，不必增加人格服务或新的稳定端口。ContextBuilder 与其组件快照读取同一份不可变人格对象；记录文本属于审计快照，不形成第二个可修改配置来源。具体配置键及装配改动在实现时确定。

示意配置（不是当前可用配置，尖括号内容均待填写）：

```yaml
assistant:
  context:
    personality:
      id: <待选人格>
      version: <明确版本>
      resource: classpath:prompts/personality/<id>/<version>.txt
      sha256: <该版本内容的完整校验和>
```

装配与使用：

```text
发布清单
  ├─ 基础提示词引用 → 读取/校验 → 基础快照
  └─ 人格提示词引用 → 读取/校验 → 人格快照
                                  ↓
ContextBuilder（接收同一批已冻结快照）
  → 系统上下文：基础规则 + 人格内容
  → 记忆数据、选中历史、本轮完整消息
  → 模型请求

执行 manifest 记录基础快照及 ContextBuilder 中实际采用的人格快照
```

| 约束 | 实现时要求 |
| --- | --- |
| 精确选择 | 不选择 latest，不在指定版本缺失时偷偷回退；错版本或校验和不符拒绝装配 |
| 保留旧行为 | 新能力使用新 ContextBuilder 行为版本与新发布清单；旧实现、旧提示词、旧清单保留 |
| 一轮稳定 | 一轮的配置从创建到终态保持一致，不中途重读可变资源 |
| 无额外推理 | 人格组合本身不调用模型，文本计入现有上下文预算 |
| 数据边界 | 用户记忆和外部文本保持数据身份；人格不授予新的工具权限 |
| 兼容历史 | 不给旧 manifest 补造人格信息，不改写旧聊天；新增配置快照值保持不可变、JSON 可序列化且无凭据 |
| 当前规模 | 第一版按装配选择一套人格；每个会话独立选角色需另外设计明确绑定，当前不声称支持 |

## 逐步完善：固定核心与可积累表达

固定版本表示某次装配采用的核心文本不可变，不表示助手只能永远重复同一组说法。人格提示词提供底色，记忆与行为可以让表达逐步贴合用户；这些仍属于既有三块，不新增“进化模块”。

| 完善方式 | 怎样变化 | 本项目归属与版本关系 |
| --- | --- | --- |
| 用户偏好积累 | 例如用户明确说“可以抽象一点，但不要句句都玩梗”，保存这一表达偏好 | MemoryModule 保存带来源的偏好；ContextBuilder 召回并作为数据提供，不覆盖核心人格资源 |
| 表达习惯积累 | 从真实交流提炼“某种场景适合怎样表达”，后续按场景选择使用 | 候选和来源可放在记忆中；选择与使用属行为，ContextBuilder 只组织选中内容；当前未实现 |
| 核心人格迭代 | 将长期有效、经过整理的设定或示例写成下一版人格提示词 | 发布新版本并明确装配选择；保留旧版，不修改已发布资源，也不在一轮中途改变版本 |

### 本项目当前选择

用户已明确偏好“活泼、跳脱、抽象、带一些黑色幽默”；已按这一方向实现 lively-companion@1.0.0。后续根据真实对话反馈校准程度，修改内容时新增版本。

当前先完成独立人格类，后续再实现资源加载、精确版本装配与上下文接入；初期通过明确反馈积累表达偏好。自动提炼表达作为后续可选能力，需明确来源、纠正方式、使用范围与调用预算。若引入额外模型学习，必须有显式执行与计数机制，不能在记忆 observe 或上下文构建中无预算地调用。

可参考的后续流程（设计建议，尚未实现）：

```text
真实交流与明确反馈
  → 带来源的偏好或表达候选
  → 筛选、纠正与场景选择
  → ContextBuilder 组织为本次参考数据

经过整理且适合长期固化的内容
  → 新人格提示词版本
  → 下一次装配明确选择
```
