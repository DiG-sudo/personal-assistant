# 参考项目的人格可选设定

阅读日期：2026-10-29（Asia/Shanghai）。本页基于实际读取的源码，区分“项目内置预设”和“用户可编辑字段”；未直接采用参考项目的具体预设；本项目已按用户方向设计 lively-companion@1.0.0，见人格设计文档。

## Hermes：内置 14 种风格预设

来源是 personality.py 的 BUILTIN_PERSONALITIES、available_personalities、render_personality_prompt 和 resolve_personality，而非界面文案。

| 预设 ID | 含义概述 | 主要影响 |
| --- | --- | --- |
| helpful | 友好、愿意提供帮助 | 基础交流态度 |
| concise | 简短、直达重点 | 回复长度与信息组织 |
| technical | 技术专家，重视准确与细节 | 专业解释方式 |
| creative | 创意表达，尝试新思路 | 思路和表达变化 |
| teacher | 耐心讲解，使用例子 | 教学方式 |
| philosopher | 关注原因、意义与深层问题 | 思考与讨论方式 |
| kawaii | 可爱、热情，使用可爱符号 | 语气与符号习惯 |
| catgirl | 动漫猫娘角色及猫式口癖 | 角色身份与语言习惯 |
| pirate | 海盗船长及航海用语 | 角色与措辞 |
| shakespeare | 莎士比亚式戏剧表达 | 修辞与语言风格 |
| surfer | 松弛、随性的冲浪者口吻 | 语气与俚语 |
| noir | 黑色侦探叙事 | 叙述方式与氛围 |
| uwu | 卖萌式拼写与表情 | 拼写与表达形式 |
| hype | 高能、兴奋、鼓动式表达 | 情绪强度与语气 |

这些预设大多是短提示词覆盖层，不是 14 套完整的长期人格系统。none/default/neutral 等名字表示不使用该风格覆盖层，不等于删除 SOUL 身份内容。

自定义定义支持文本，或包含 system_prompt、tone、style 的对象；description 用于列表预览。用户配置可按名字覆盖内置定义，agent.personalities 在同名时优先于顶层 personalities。这个优先级是 Hermes 的实现，本项目不必照搬其热切换和同名覆盖机制。

源码：R17。

## SillyTavern：可编辑角色卡

它提供角色信息的字段体系；这些字段的内容主要由角色卡作者填写，不是“温柔/高冷”等固定枚举。

| 字段 | 可填写的内容 | 对本项目的归属 |
| --- | --- | --- |
| name、description | 名称、身份、背景和角色描述 | 人格核心设定 |
| personality | 性格特点和相处方式 | 人格核心设定 |
| scenario | 场景与背景约定 | 静态角色场景可归人格；当下真实情况由上下文提供 |
| mes_example | 示例对话 | 人格对话示例 |
| first_mes、alternate_greetings | 开场白和替代开场白 | 后续行为/界面能力，第一版人格提示词不自动发送 |
| system_prompt、post_history_instructions | 主提示词与靠近历史的补充指令 | 参考其提示词位置思想，当前不照搬权限覆盖及深度插入 |
| character_book | 世界观或角色相关资料 | 若有实际需求，纳入资料/记忆检索设计 |
| character_version、tags、creator_notes 等 | 版本、检索标签及作者元信息 | 配置或展示元信息，不等于都应发给模型 |

char-data.js 定义字段；TavernCardValidator.js 校验角色卡结构；实际组装路径另见 R01 的 openai.js。字段存在并不表示它每轮都进入系统提示词。

源码：R18、R19。

## AIRI：角色卡与一个内置 VTuber 人设

| 项目 | 已读代码中的内容 | 可借鉴点 |
| --- | --- | --- |
| 人格内容 | resolveSystemPrompt 组合 systemPrompt、description、personality、scenario 等文本 | 身份、性格、场景和提示内容可组合 |
| 默认描述 | base.prompt.prefix 提供实验性虚拟 VTuber 的身份背景、动漫式可爱表达和简单短回复；带虚构角色故事 | 展示一个完整角色怎样把背景和语言习惯放在一起；不是本项目已选人设 |
| 默认卡绑定 | builtInCard 使用 base.prompt.prefix 作为 description；卡名与描述文本中的自称并不完全相同 | 必须核查最终组装文本，不能只看卡名就推断人格 |
| 角色展示 | 卡还能绑定形象、语音及其他模块 | 这些是展示与能力设置，不需要纳入当前纯文本人格版本 |

该默认描述还含有可自由想象过去及强调真实存在的角色扮演设定。这里记录源码事实；本项目未选择该人设，也不会把虚构背景写成真实共同经历。

源码：R02、R20、R21。

## MaiBot：人格与表达风格分开

| 配置 | 已读源码中的可选内容 | 运行方式 |
| --- | --- | --- |
| personality | 自由文本，填写身份、性格；默认是带日常群聊特点的女大学生角色，也含较锐利的表达设定 | 生成固定人设提示，组合名称/别名 |
| reply_style | 自由文本，默认偏平淡、简短、随意口语 | 基础表达风格 |
| multiple_reply_style | 备用风格包含白话讽刺、极短文字、极短符号、古雅文言、翻译腔 | 只影响本次回复 |
| multiple_probability | 0—1 的触发概率；当前配置定义默认 0 | 0 关闭随机备用风格；生成器也检查该值 |
| behavior_style | Planner 的行动准则，如参与、观察、保持安静 | 在本项目归行为，不混作固定人格字段 |

第一版可借鉴“身份/性格”与“表达风格”的区分。随机切换表达不是稳定人格的必要机制，暂不纳入本项目默认方案。

源码：R22、R23。

## 本项目的人设候选维度

以下是依据上述机制整理的可选维度，不是参考仓库内置的统一枚举，第一版已据此设计为 lively-companion@1.0.0；后续仍可按新版本调整，状态列区分用户要求与设计取舍。

| 维度 | 可讨论的方向 | 当前状态 |
| --- | --- | --- |
| 相处方式 | 工作伙伴、日常朋友、耐心导师、虚构角色陪伴 | 第一版设计为熟悉、好聊、有自己判断的搭档，不预设恋爱关系 |
| 性格 | 温和/直率，沉稳/活泼，包容/有锋芒 | 用户明确活泼、跳脱；第一版补充好奇、善意和有判断 |
| 表达 | 简洁/细致，克制/热情，正式/口语，幽默方式与程度 | 用户明确抽象与一些黑色幽默；第一版有场景收放原则，模型效果待验证 |
| 观点与价值 | 怎样表达分歧、面对不确定性、提供支持 | 第一版有理由地表达分歧，不编造记忆，关心具体且尊重自主选择 |
| 示例 | 闲聊、工作、失落、分歧等场景的具体回复 | livelyV1() 已包含八组 |

人格版本选择解决“装入哪一份已确定内容”；这些维度帮助编写内容，第一版不需要把每个维度都变成配置开关。
