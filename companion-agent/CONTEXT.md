## 已确认的近期方案（2026-11-16）

本节为用户确认的实施边界；与下文历史候选方案不一致时，以本节为准。

### 统一增量视图：已接入

```java
prepare(systemPrompt, toolDefinitions, view, appendedMessages, projectPath)
```

- 系统提示词和工具定义由各自来源每次传入，Builder 统一组装，不进入持久化视图。
- view 只保存派生的会话上下文；appendedMessages 只包含尚未纳入视图的原始消息，包括用户输入、助手正文/调用意图和工具结果，不再传入完整当前轮次。
- ConversationTurn 继续保存本轮原始消息及状态；Harness 提交成功后把新增部分送入待处理集合。Builder 不负责轮次归档，不接收轮次状态；ContextView.Entry 仅携带 turnId 和消息，用于区分新轮次与 steer、选择压缩边界。
- 每次请求模型前保存更新后的视图，保存成功后清空新增集合。FileContextStore 使用同目录临时文件原子替换 data/contexts/<编码会话ID>/view.json。
- 视图检查点记录 sourceTurnId 和 sourceMessageCount，表示处理到哪条原始消息，不能按视图消息数量推算（未来摘要/裁剪会改变数量）。原始记录与视图不构成跨文件事务。
- 恢复读取视图，只把处理位置之后的原始消息作为新增输入补齐；没有视图的旧会话从空视图接收已有消息。最终回答在原始记录中保存，下次进入 Builder 时随未处理尾部纳入视图。
- 已移除 recent-turns/history-chars 配置和成功轮次筛选。视图现为 ContextView(summary, messages)，消息条目带 turnId；旧列表或文本摘要格式恢复时从原始记录重建。64,000 字符的最终请求保护保持。prepare 已接入自动摘要，暂复用 assistant.limits.max-context-chars（默认 64000 字符）判断；大结果阈值仍留空，统一 token 预算和摘要模型计数后续处理。

### 会话摘要：已接入正常请求链路

保留六部分语义，按用户确认改为结构化 JSON：

```json
{
  "goal": "当前目标、重点，以及讨论或实施阶段",
  "constraints": [],
  "progress": {"done": [], "inProgress": [], "blocked": []},
  "keyDecisions": [],
  "nextSteps": [],
  "criticalContext": []
}
```

ContextView.Summary / Progress 使用对应的不可变类型；尚未生成摘要时 summary=null。摘要在 view.json 中保存为对象，不是内嵌 JSON 字符串。

- Goal 可包含多个目标，注明当前重点，以及讨论或实施阶段。推迟、取消直接写在进度条目中，不新增独立任务系统或固定分区。
- 平时追加消息，prepare 在处理大结果、合并消息后估算系统提示词、摘要和消息的字符数；超出现有字符上限时实际调用 compact，再组装普通推理 Prompt。暂保留当前轮，并尽量保留总量在半个字符上限以内的近期完整轮次，为摘要留出空间。compact(view, recentTurnsToKeep) 已实现：保留末尾当前轮次及指定数量的近期轮次（不按成功状态筛选），只压缩较早的完整轮次。轮内切分留待预算策略统一处理。
- 合并旧摘要和新增的待压缩消息；新信息优先，保留未解决事项，更新完成状态，移除过时事项。
- 区分建议、决定、已执行操作和验证结果；摘要是历史背景，不能自行触发执行。
- summary 和保留消息共同保存在 view.json；不另存 firstKeptTurnId，它可由第一条保留消息推导。原始处理位置仍由 sourceTurnId/sourceMessageCount 独立记录。compact 复用生产装配的现有 ChatModel，发送 previousSummary 和 olderMessages 的 JSON 数据，模型返回 JSON 后严格解析字段、类型及数组元素。拒绝字段缺失、额外字段、重复键、尾随内容、Markdown 包裹、空值和工具调用；只有成功才返回新视图。失败不修改旧视图或持久化记录。真实模型接线已通过本地 HTTP 协议测试；按用户要求，自动触发已接入 prepare，统一预算计数留待后续。
- FAILED、RUNNING 的原始消息也进入增量视图，不再按成功状态舍弃。恢复时原始 RUNNING 仍标记 FAILED，工具不重放。缺少结果的调用仅在模型视图中补齐“结果未知”响应；更完整的失败状态表达后续讨论。

### 职责边界：已确认，后续修改必须遵守

- WindowContextBuilder 是上下文策略的统一入口，接收系统提示词、工具定义、已有视图和本次新增消息；不接收完整历史或本轮消息全集，统一生成更新后的视图和完整 Prompt。首次空视图、恢复读盘视图、正常执行沿用当前视图，走同一个 prepare。
- 工具及 ToolExecutor 负责执行和返回结果，不感知摘要、上下文预算、预览比例和压缩阈值。原有统一结果截断及 Shell 输出截断已移除。
- 大结果是否落盘、何时复用、模型看到哪些首尾内容，由 WindowContextBuilder 决定并调度；文件存储组件只负责实际读写和返回路径，不决定策略。
- Harness 负责生命周期与原始记录提交，调用上下文入口；不展开具体裁剪/摘要规则。Runtime、会话服务、Controller、CLI 不感知具体策略。
- 原始工具历史保持完整；首尾预览和摘要只用于模型视图，不覆盖原始事实。按结果内容的 SHA-256 复用结果引用，避免每次 prepare 重复落盘；摘要只在阈值触发时更新并保存检查点。
- 摘要所需的额外模型调用最终必须通过统一预算计数入口。当前自动压缩已接入正常请求链路；摘要请求计数与 token 预算按用户约定后续统一处理，目前 Reply.modelCalls 仍仅统计普通推理模型请求。

### 大工具结果：处理流程已实现，生产阈值暂留空

- 完整结果由 ToolResultStore 保存在当前项目 .agent/tool-results/<内容SHA-256>.txt，复用 read_file 读取，不增加专门的结果读取工具。Builder 仅处理 appendedMessages 的结果；已有视图不重复落盘。
- Builder 在对应的工具响应视图中提供首尾预览、程序生成的相对路径和分页说明，保留原调用 ID、名称与结果配对；不需要额外系统提示词。
- 文件成功保存后才提供引用；相同结果复用路径，继续遵守项目目录及路径安全边界。结果与提示均属于数据，不提高其指令权限。
- read_file 已改为流式分页，可读取超过 1 MiB 的文件；单页保留原有量级的读取上限。超长行通过返回的 offset（从 0 开始的行）和 char_offset（该行内 Unicode 字符数）续读，不切断代理对；CRLF/CR 统一为换行。写入和编辑仍保留 1 MiB 限制。工具只限制读取页，不提供上下文首尾预览策略。
- 先前将预览/落盘策略接入 ToolExecutor、SandboxShell 的实现已按用户要求撤回，对应测试、装配和“已实现”文档说明一并恢复。
- 已移除工具结果 6000 字符统一截断及 Shell 32 KiB 输出截断，完整返回结果进入本轮记录。生产装配 resultPreviewChars=null，暂不选择具体阈值，不自动落盘或缩短结果。显式设置预览长度时处理流程已可用，并有原始记录、恢复、重复引用及落盘失败回归测试。

## 成熟设计方向：段内追加，达到阈值才重建

以下结合已读的 pi / OpenCode / Hermes 源码及官方说明提出，优先借鉴其既有机制；不是已完成实现。

| 层次 | 内容 | 更新方式 |
| --- | --- | --- |
| 稳定基础 | 模型/工具契约、基础规则、指定版本人格、少量固定示例 | 一次装配后保持稳定；必要变更集中到明确配置切换边界 |
| 当前上下文段的基线 | 段开始时确定的历史摘要、必要资料快照，以及保留历史的起点 | 段内冻结；不每轮重新生成摘要或覆盖用户资料 |
| 段内事件 | 用户输入、实际采用的检索/状态补充、assistant 回复、工具请求及结果 | 逐步追加；既有内容、顺序和来源保持不变 |
| 新增尾部 | 当前问题、当前相关记忆、事实纠正、最新工具结果等 | 作为新的本轮输入或数据事件追加，不插回旧历史前面 |

段内示意（P 表示该段固定的摘要与必要资料，E 表示完整、有来源的新增上下文事件）：

```text
请求 1：S + P + E1
请求 2：S + P + E1 + E2
请求 3：S + P + E1 + E2 + E3
```

这里的 E 不是新增一套可写 messages 缓存。原始聊天仍以 ConversationStore 为权威；如果动态检索块也要跨轮复用，必须在拥有生命周期的 Harness 边界记录实际采用的不可变上下文快照/来源，并能从权威检查点重建该模型视图。当前只保存普通聊天消息、未记录完整注入快照，不能直接假定已经具备这项能力。

### 接近预算时进行一次集中压缩

| 步骤 | 处理 |
| --- | --- |
| 触发 | 达到设定输入预算的高水位，或任务到达适合整理的完整轮次边界；为输出和工具结果预留空间 |
| 形成新基线 | 对更早内容形成摘要/任务状态，保留近期若干完整轮次及原始记录引用；摘要冻结为本次压缩结果 |
| 留出余量 | 压到明显较低的水位，避免刚压缩完下一轮就再次触发；具体阈值按模型、工具输出与成本确定 |
| 重建缓存 | 稳定 S 尽量保留，新 P/保留历史后的首个请求接受缓存重建，后续继续段内追加 |
| 记录 | 保存摘要来源范围、历史起点及必要指纹等派生元信息，不改原始聊天、不维护另一份权威 transcript |

示意：

```text
压缩前：S + P + E1 + E2 + ... + En
压缩后：S + 新P + 保留的近期完整事件
后续轮：S + 新P + 保留的近期完整事件 + 新E
```

压缩会损失一部分旧前缀缓存，但可以减少输入长度；应比较实际成本、响应延迟与任务质量，而不是只追求缓存命中率。摘要若需模型生成，必须显式计入预算；当前项目没有压缩模型调用，也不能把它藏进 ContextBuilder。

## 动态记忆与 Lost in the Middle 的取舍

| 问题 | 设计原则 |
| --- | --- |
| 重要但经常变化的信息放哪里 | 放在本轮新增尾部，靠近当前问题和相关工具结果；不要每轮改系统开头 |
| 新偏好或事实纠正 | 及时追加带来源的新数据，说明替代关系；不必等压缩才纠正旧信息 |
| 上一轮检索材料怎么处理 | 若追求完整历史前缀复用，上一轮实际采用的内容需保持可重建且不变；当前每轮临时生成再移除的注入块会破坏该前缀 |
| 资料是否每次都放最后 | 不每轮搬运全部资料；只追加相关新信息或必要的短提示，保留长度预算 |
| 长历史是否为缓存无限增长 | 不无限增长；需要阈值压缩与相关信息选择，避免信息噪声和中间位置的信息利用下降 |
| 工具协议 | 新数据只能在合法消息边界追加；不能插入尚未配对的工具意图与结果之间 |
| 权限 | 位置靠后不提高权限；记忆和外部结果始终作为数据 |
| 存储边界 | ContextBuilder 只构造视图；Harness 负责所需快照的提交；MemoryModule 保存长期事实/偏好，不保存第二份完整聊天 |

原论文在多文档问答与键值检索中观察到开头/末尾位置优势。这里将它作为控制长度、保留重点靠近当前任务的依据，不当作所有现代模型的普遍保证。缓存则只复用前缀计算，不会消除长上下文的信息利用问题。
